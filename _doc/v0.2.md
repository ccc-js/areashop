## 2. 實際交付

### 後端（`backend/src/`）
- entities：`service`（`daily_capacity` 遺留欄位恆寫 1，只為相容舊庫 NOT NULL，不再使用）、`availability_rule`（weekday 0=週日..6=週六，windows JSON `[{start,end}]`）、`availability_exception`（date TEXT、`full` 額滿旗標；舊庫啟動時 ALTER 補欄，舊 `capacity_override` 留著不用）、`appointment`（date TEXT、window、note）；`schema.rs` 建表＋唯一索引（範本一天一條、例外一天一條）。
- 純函數 `booking.rs`：`Window{start,end}`＋`valid_window`＋`parse_windows`（舊字串格式寬容讀取）＋`resolve()`（例外＞範本＞無規則即休；可約 ⇔ open 且非 full）＋日期/月份工具；`appointment.rs` 狀態機。全 repo 共 8 個 `cargo test` 全過。
- routes：`services.rs`（CRUD＋rules＋exceptions upsert/刪除＋`GET /services/:id?month=` 日狀態）、`appointments.rs`（`POST` 201 只擋關閉/額滿/重複、`GET` buyer/seller＋from/to、`GET /:id`、`PATCH`、`GET /provider/calendar` 按日聚合）。
- 取消期限：`now >= 當日 00:00 UTC − cancel_hours` 回 422。

### 前端（`frontend/src/`）
- `/s/:id` 月曆選日（休/滿禁用，顯示 休/滿/可約）→ `/book/:serviceId` 填需求說明送出 → `/appointments[/:id]` 買家/賣家頁籤＋狀態按鈕；`/provider` 選店→選項目→週範本（每天開關＋起點/終點輸入＋逐條刪除）→月曆點日→日明細（三選一＋備註）。Home 可預約區只顯示標題＋價格。
- `npm run build` 通過；沿用 `.cal/.day` 樣式。

## 3. 與 plan0.2 的差異（實作時的小取捨）

1. 重複預約擋法：用 transaction 內檢查而非 DB unique index（SQLite/PG 錯誤訊息不一；註解已標 MVP）。
2. `GET /services/:id` 無 month 時預設本月 UTC；取消期限以 UTC 午夜計（顯示未轉 Asia/Taipei，v0.4 再做時區）。
3. Playwright 未加（plan §7 有列；目前 e2e 是 `test.sh` curl 版，與 v0.1 一致）。
4. 遺留相容：舊庫 `services.daily_capacity`、`availability_exceptions.capacity_override` 欄位保留不用；舊字串式 windows 讀取時轉成對，PUT 一律寫新格式。

## 4. 已知限制 / 技術債

- 人數不進系統是刻意設計：很多買家不走系統（現場客、電話、熟客），系統算的人數永遠對不上；實體小店/自由接案者/家庭商店由店家自己勾額滿。
- 區段只檢查 HH:MM 格式＋起點＜終點，不檢查重疊。
- 月曆按鈕用本地時區算週幾，跨時區顯示可能差一天。
- 舊庫也會自動補：`seed_if_empty` 分兩段——基底只在空庫塞；服務類只要 `services` 表空就補，舊庫重開即有。店名/項目已在就沿用不覆蓋。
